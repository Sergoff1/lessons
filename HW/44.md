#### Пример 1

У нас есть хранилище паблишеров, которые занимаются отправкой сообщений во внешние системы. Хранилище используется в сервисе и конвертерах.
В каждом месте данные паблишеров удобнее получать по своему. В одном из таких мест нам было бы проще доставать информацию о конфиге по идентификатору паблишера, а не по его классу.
Мы можем создать новую мапу `Map<String, OutboxPublisherConfig> idToConfig;`, где ключом служил бы идентификатор паблишера и добавить новый метод для обращения к ней и получения конфига паблишера по идентификатору.
Это упростит код в одном из сервисов. Также мы можем сделать аналог view, из которого можно получать эти же данные.
В примере ниже я добавил функцию `getConfig(String publisherType)`, которая является аналогом view и возвращает нужные данные по более удобному для нас ключу. 
Преимущество данного подхода в том, что нам не нужно следить за синхронизацией данных между двумя мапами.

До:
```java
public class OutboxPublisherRegistry {
    private final Map<Class<? extends OutboxPublisher>, OutboxPublisherConfig> classToConfig;
    private final Map<String, OutboxPublisher> idToPublisher;

    public OutboxPublisherRegistry(List<OutboxPublisher> publishers, List<OutboxPublisherConfig> configs) {
        Map<Class<? extends OutboxPublisher>, OutboxPublisher> classToPublisher = publishers.stream()
                .collect(Collectors.toMap(OutboxPublisher::getClass, Function.identity()));

        this.classToConfig = configs.stream()
                .collect(Collectors.toMap(OutboxPublisherConfig::getPublisherClass, Function.identity()));

        this.idToPublisher = configs.stream()
                .collect(Collectors.toMap(OutboxPublisherConfig::getPublisherType,
                        config -> classToPublisher.get(config.getPublisherClass())));

    }

    /**
     * Возвращает бин паблишера по его ID (publisherType).
     */
    public OutboxPublisher getPublisher(String publisherType) {
        OutboxPublisher publisher = idToPublisher.get(publisherType);
        if (publisher == null) {
            throw new IllegalArgumentException(
                    "Паблишер " + publisherType + " не зарегистрирован.");
        }
        return publisher;
    }

    /**
     * Возвращает бин конфига паблишера по классу.
     */
    public OutboxPublisherConfig getConfig(Class<? extends OutboxPublisher> publisherClass) {
        OutboxPublisherConfig config = classToConfig.get(publisherClass);

        if (config == null) {
            throw new IllegalArgumentException(
                    "Конфигурация паблишера " + publisherClass.getName() + " не зарегистрирована.");
        }
        return config;
    }
}
```

После:
```java
public class OutboxPublisherRegistry {
    //Выше всё то же самое
    
    /**
     * Возвращает бин конфига паблишера по его ID (publisherType).
     */
    public OutboxPublisherConfig getConfig(String publisherType) {
        OutboxPublisher publisher = idToPublisher.get(publisherType);
        return getConfig(publisher.getClass());
    }
}
```

#### Пример 2
У нас есть два связанных ДТО, которые представляют одну сущность для разных потребителей. Периодически нам нужно перегонять данные из одного ДТО в другой.
В одном ДТО список устройств представлен id, а в другом -- именем. Данные об устройствах достаются из другого сервиса и кэшируются в мапе, отражающей id на имена устройств.
При преобразовании из первого ДТО во второй мы достаём данные за O(1), но при обратном преобразовании нам приходится бегать по всем значениям мапы.
Для решения этой проблемы можно завести вторую мапу, которая будет отражать имя устройства на его идентификатор. Тогда в каждом конвертере мы будем относительно легко получать нужные значения за O(1).
Логика при этом не усложняется и следить за синхронностью мап особо не надо. Они являются справочными и данные берутся из стороннего сервиса, мы же их просто периодически обновляем на своей стороне.

До:
```java
public class CacheService {
    //...

    @Cacheable("deviceTypeIdToNameMap")
    public Map<Long, String> getDeviceTypeIdToNameMap() {
        log.info("Start getDeviceTypeIdToNameMap()");
        return ncClient.deviceTypes().getItems().stream()
                .collect(Collectors.toMap(NcDeviceType::getId, NcDeviceType::getName));
    }
    
    //...
}
```

После:
```java
public class CacheService {
    //...

    @Cacheable("deviceTypeIdToNameMap")

        log.info("Start getDeviceTypeIdToNameMap()");

                .collect(Collectors.toMap(NcDeviceType::getId, NcDeviceType::getName));
    }
    
    //...
}
```

#### Пример 3
Приложение автопарка с дипломного проекта. Там есть места, где выполняется проверка прав доступа менеджера. 
Например, что он может редактировать информацию конкретного автомобиля. Сейчас, для того, чтобы убедиться в правомерности доступа, приходится доставать данные менеджера из БД, а ещё
данные автомобиля и данные предприятия, к которому относится автомобиль. Много действий и несколько запросов к БД. 
Кажется, что здесь можно повысить информационную избыточность, создав отображение менеджер -> автомобиль или менеджер -> предприятие. 
Это позволит сократить количество походов в БД и упростить логику проверки прав доступа. Предприятия создаются не очень часто, поэтому проще работать с условной мапой менеджер -> множество предпрятий.
Для проверки прав доступа смотрим, что менеджер из текущей сессии имеет доступ к предприятию, чей автомобиль меняется. По менеджеру получаем список доступных предприятий и вызываем contains с предприятием автомобиля.
По сути у нас получается кэш/материализованное представление, но его необходимо обновлять. Это можно привязять к методам изменения предприятий/менеджеров. Логика стала чуть сложнее из-за необходимости синхронизации мапы с БД, но выполнять проверки стало проще.

### Выводы
Очень полезное для меня занятие. Несколько иначе взглянул на информационную избыточность. Идеи free object я помню, там тоже обсуждалась избыточность,
но в моей голове по free object отложилось то, что он помогает повысить гибкость кода, которая позволяет нам относительно безболезненно менять архитектуру и структуры данных.  
Здесь же избыточность упрощает API и "повседневное" взаимодействие с кодом. Раньше я почти всегда стремился к краткости, минимуму источников данных. 
Но в ходе этого занятия увидел как избыточность может упрощать жизнь и понял, что эта избыточность не так уж и плоха. Моё отношение к ней несколько поменялось, теперь буду меньше возмущаться, когда увижу информационную избыточность в коде.
Но стоит помнить, что эта штука не является серебрянной пулей и за применение избыточности часто придётся платить усложнением логики и появлением новых потенциальных ошибок. 
А значит, прежде чем тащить её в проект, нужно подумать какие плюсы она даёт и какие риски она несёт. После чего принимать решение. 
В ходе выполнения задания я понял, что иногда избыточность может неплохо упрощать жизнь без серьёзного усложнения логики, но иногда придётся здорово подумать над синхронизацией этих избыточностей.
